# Go Worker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement a horizontally scalable Go worker that atomically claims PostgreSQL jobs, executes them with bounded concurrency, maintains leases and heartbeats, and shuts down gracefully.

**Architecture:** A small pgx repository owns SQL and transactions. A worker coordinator combines PostgreSQL notifications with periodic polling, dispatches claims into a bounded goroutine pool, and uses lease tokens on every state mutation. Handler implementations return a common result rather than mutating persistence directly.

**Tech Stack:** Go 1.24, pgx/v5, Prometheus client_golang, slog JSON logging, net/http, httptest, Testcontainers Go, and the standard testing package.

## Global Constraints

- Own only `services/worker/**`.
- The database schema from `services/api/migrations/versions/0001_initial.py` is authoritative.
- Use `WORKER_DATABASE_URL` and the canonical environment names from the master plan.
- Every completion, failure, heartbeat, and lease extension must guard on job ID, worker ID, and lease token.
- Bound concurrent executions; never create one unbounded goroutine per claimed job.
- A PostgreSQL notification is only a wake-up hint; periodic polling is mandatory.
- Do not execute arbitrary shell commands or source code from payloads.
- Do not edit root README or deployment files; report required changes to root.

- [ ] **Step 5: Implement retry calculation and atomic claim SQL**

Retry delay is `base`, `base * attempt`, or `base * 2^(attempt-1)` for fixed, linear, or exponential strategies, capped at `MaxDelay`. Use overflow-safe duration arithmetic.

Use one transaction with this shape:

```sql
WITH queue_usage AS (
  SELECT q.id, q.concurrency_limit,
         count(jr.id) FILTER (WHERE jr.status IN ('claimed','running')) AS active
  FROM queues q
  LEFT JOIN jobs jr ON jr.queue_id = q.id
  WHERE q.paused_at IS NULL
  GROUP BY q.id
), candidates AS (
  SELECT j.id
  FROM jobs j
  JOIN queues q ON q.id = j.queue_id
  JOIN queue_usage u ON u.id = q.id AND u.active < u.concurrency_limit
  WHERE j.status IN ('queued','retry_scheduled')
    AND j.scheduled_at <= now()
    AND j.lease_expires_at IS NULL
  ORDER BY
    (q.priority + j.priority + LEAST($4,
      floor(extract(epoch FROM (now() - j.scheduled_at)) / $3))) DESC,
    j.scheduled_at ASC, j.id ASC
  FOR UPDATE OF j SKIP LOCKED
  LIMIT $1
)
UPDATE jobs j
SET status = 'claimed', claimed_by_worker_id = $2,
    lease_token = gen_random_uuid(),
    lease_expires_at = now() + $5::interval,
    updated_at = now()
FROM candidates c
WHERE j.id = c.id
RETURNING j.*;
```

Insert the execution attempt and claimed state event in the same transaction. If queue concurrency must account for multiple candidates in the same batch, cap candidates per queue by remaining slots with a window rank before the final limit.

For queues with `rate_limit_per_minute`, the same claim transaction locks the eligible queue row, refills `rate_tokens` from elapsed database time up to the configured capacity, ranks candidates against the available whole-token count, and subtracts one token per claimed job. Queues without a rate limit bypass this calculation. Add a concurrent repository test proving total claims cannot exceed the available tokens.

- [ ] **Step 6: Implement all fenced state mutations**

Every update predicate includes:

```sql
WHERE id = $job_id
  AND claimed_by_worker_id = $worker_id
  AND lease_token = $lease_token
  AND lease_expires_at > now()
```

Return `false, nil` when zero rows are affected. Complete/fail transactions insert logs, update the execution attempt, update the job, and append the state event atomically.

`Fail` uses the claimed retry policy snapshot. Retryable failures with remaining attempts transition to `retry_scheduled` and clear claim ownership after assigning `scheduled_at`. Non-retryable or exhausted failures create the DLQ entry and transition to `dead_lettered` in the same transaction.

- [ ] **Step 5: Implement the bounded execution pool**

Use a fixed number of worker goroutines consuming a bounded channel. Submission returns `ErrPoolFull` rather than blocking the coordinator indefinitely. Each execution marks running, derives a child context with the job's `Timeout`, starts a lease extender, invokes the handler, stops the extender, and performs a fenced complete or fail transaction. Deadline expiry produces a retryable `execution_timeout` result.
